# AURA — what is left to build

Ordered by what buys the most. Each item says what exists now, what "done" means, and
where the work goes. Anyone picking this up should be able to start at the top.

Status as of 2026-09-04.

---

## 0. First, what is already real and what is not

Be precise about this in front of a judge. Overclaiming here is the fastest way to lose.

| Piece | State | Note |
|---|---|---|
| Decision engine, admission, eviction, policy blending | **Real** | Genuine algorithms, exercised on every request |
| Cost accounting and the benchmark | **Real** | Same stream through every policy, Belady bound computed |
| Cached bytes in memory | **Real, with `--real-values`** | Without the flag the pool is an accounting number and holds no payload |
| Rebuild cost for analytics | **Real, with `--real-backend`** | Without the flag the figure comes from the generator |
| Traffic | **Simulated by default** | The engine's own generator. Real traffic needs `apps/` running, see item 1 |
| Model | **Untrained** | Online logistic fallback until a bundle is published |

Two flags flip most of that:

```
cargo run --release -p aura-server -- --scenario mixed_production --real-values --real-backend
```

`--real-values` was measured at 1.19 GB resident for an 800 MB pool. It is real memory.

## 1. Run the demo on real traffic instead of the simulator

**Why first.** The single weakest sentence in the current demo is "this traffic is
generated by the cache itself". Everything needed to remove that sentence already exists
and is not being used.

**What exists.** `apps/common/aura_client.py` already does the full loop over HTTP: GET the
cache, on a miss run the real work, measure what it cost, PUT it back with the measurement.
`apps/driver/run_universe.py` already spawns the three services and drives load.
`apps/analytics/db.py` already talks to Supabase Postgres via asyncpg and falls back to a
local SQLite fixture.

**What to do.**

```bash
# terminal 1 — engine with NO --scenario, so the internal generator stays off
cd engine
cargo run --release -p aura-server -- --real-values

# terminal 2 — the applications, which become the traffic
cd apps
pip install -r requirements.txt
python -m driver.run_universe --spawn --rps 200 --duration 300
```

**Done means.** The dashboard's traffic-source banner reads "live applications", the
per-application panel fills from real services, and `db_ms` comes from asyncpg round trips
rather than the generator.

**Closed.** `apps/common/settings.py` accepts the unprefixed `SUPABASE_DIRECT_CONNECTION_URL`
and `SUPABASE_TRANSACTION_URL` names that `backend/.env` already uses, so no export is
needed. `GET /health` on the analytics app reports which backend it actually opened.

## 2. Two real cache tiers, not one

**Why.** The current L1 is a recency *window* used as an admission filter, not a cache: it
stores no values. There is no shared tier at all. The distinction between a per-process
local cache and a shared network cache is the one that makes an architecture argument, and
right now the diagram claims a hierarchy the code does not have.

**Target shape.**

| Tier | Lives | Holds | Miss falls to |
|---|---|---|---|
| L1 | inside each app process | tiny, hot, seconds of TTL | L2 |
| L2 (AURA) | one shared service | the scored, cost-aware pool | application service |
| origin | Postgres / GPU / API | the truth | — |

**What to do.**
- Give `apps/common/aura_client.py` a small in-process dict with a size cap and short TTL,
  checked before the HTTP call. Count its hits separately.
- Report `l1` in the telemetry frame from that, not from the admission window. Rename the
  current window to `admission_window` so it stops being mistaken for a cache.
- The engine already exposes everything an L2 needs; no Rust change is required for the
  basic version.

**Stretch.** Put Redis behind AURA as the persistence tier so a restart does not lose the
pool, which is the one thing the table above says a local cache cannot do.

## 3. Auto-scaling has to move real memory, and be visible

**What exists.** `engine/aura-server/src/capacity.rs` already does the economics correctly:
miss-ratio curve for the hit rate the next block would buy, the cost model to price it,
`net_usd_hr`, an ROI threshold and a cooldown so it cannot oscillate. `set_capacity` is
applied for real and evicts down to the new bound.

**What is missing.**
- With `--real-values` the pool is real memory, so scaling is real. Without it, it is a
  budget. Make `--real-values` the default and add `--simulated-values` for the fast path.
- Nothing plots allocation over time. A step chart of pool size rising during a spike and
  falling after is the proof the mechanism works, and it is the one chart a judge will
  remember. The history hook already records `capacity` per frame; it just needs drawing.
- Scale-down is implemented but rarely fires because pressure stays high under the default
  scenario. Verify it on `steady_zipf` after a flash crowd subsides.
- No host memory awareness. `host_budget_bytes` is a config constant, not a reading of
  actual free RAM.

## 4. Train and publish a model

**What exists.** The whole pipeline: `training/aura_train/` builds a dataset, trains GBDT
and linear heads, evaluates with a cache replay rather than AUC alone, exports the portable
bundle and uploads it. `training/tests/test_features_parity.py` proves the Python and Rust
feature builders agree.

**What to do.** Run `training/notebooks/aura_training_colab.ipynb` end to end with the two
Supabase secrets set. Then press "Load from Supabase" on the Model tab, or
`POST /v1/model/reload {"source":"supabase"}`.

**Note on data.** `TRACE_SOURCE = "synthetic"` is the default and is the right choice: it is
the only source that carries cost metadata, which is what the economic head needs. The
public traces in `training/scripts/fetch_public_traces.sh` train the reuse head only. Say
that plainly rather than implying the model learned economics from Twitter traces.

## 5. Benchmark against modern policies, not just the classics

**Why.** The build plan sets the bar at S3-FIFO, SIEVE, W-TinyLFU, LHD, LeCaR and Cacheus.
The benchmark currently runs LRU, LFU, GDSF and cost-aware. Beating LRU in 2026 is not a
result anyone is impressed by, and someone will say so.

**What to do.** Either implement S3-FIFO and SIEVE directly in `bench.rs` — both are short,
under a hundred lines each — or export traces in libCacheSim's `oracleGeneral` format and
run the comparison there. S3-FIFO and SIEVE first: they are the cheapest credibility per
line of code in the whole repository.

---

## 6. Emit traces so the trace format has a producer

`docs/CONTRACTS.md` §4 defines a trace format. Nothing writes it. `aura-bench` as a
standalone binary with `--emit-trace` does not exist; the benchmark only runs in-process
through `POST /v1/bench/run`.

Until this exists, training cannot use real recorded traffic from your own system, which is
the thing that would make the economic head genuinely yours.

## 7. Deployment

Written, not yet run. `deploy/` holds `Dockerfile.engine`, `Dockerfile.apps`,
`Dockerfile.dashboard`, `docker-compose.yml`, `railway.json`, `render.yaml` and
`nginx.conf`; `docs/DEPLOY.md` is the step-by-step for local, Railway, Render and Vercel.

Four blockers were found by reading and are fixed: the engine image copied
`target/release/aura-server` when the binary is `aura`; the dependency layer never copied
`Cargo.lock`; neither the engine nor the applications read `PORT`, which is the only port a
Railway or Render container is routed on; and the analytics app could only use Supabase's
IPv6-only direct host, which Render cannot reach, so the transaction pooler is now a
fallback with asyncpg's statement cache disabled for it.

Still open: no authentication on any route, which matters the moment the engine has a
public URL, and no image has been built even once because there is no Docker daemon on the
build machine.

## 8. Smaller things

- **CDN layer.** Declared in the telemetry contract, not implemented. The frame omits it
  rather than reporting zeros, which is the honest choice, but the contract should say so.
- **Multi-node.** `/v1/nodes` returns one hardcoded node. Consistent hashing and `ScaleOut`
  are described but not built.
- **`observe()` is never called.** `predictor.rs` has an online update path that nothing
  invokes, so the online model never learns from realised outcomes. Wiring it means
  recording whether an admitted key was actually reused within the horizon and feeding that
  back. This is a real gap: the cold-start model is currently frozen at its priors.
- **Refresh is shallow.** `refresh_candidates` resets `inserted_ms` rather than rebuilding
  the object, so a refreshed entry serves stale bytes with a fresh timestamp. Correct
  behaviour is to call the application to rebuild it.
- **Dead code.** `cdn_stats`, `Entry::score`, `Store::contains`, `needed_bytes`,
  `context_of`, `total_hits` are unused. Either wire or remove.
- **Python comment pass.** The Rust tree was trimmed; `training/` and `apps/` were not.

1. Item 1, real traffic. It is configuration, not code, and it removes the biggest
   objection.
2. Item 3's allocation chart. One chart, high demo value.
3. Item 5, S3-FIFO and SIEVE. Cheap credibility.
4. Item 4, train the model, so the predictor reads `gbdt`.
5. Item 2, the real two-tier hierarchy.
6. Item 7, deployment, only if there is time.
